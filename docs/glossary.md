# Glossary

Use these terms in current repository prose. Definitions summarize the linked
accepted ADRs and normative specifications; they do not replace them. Follow the
[authority order](../AGENTS.md#authority-order) when sources disagree. Preserve
exact code and protocol identifiers, quoted wording, and historical records.

## Identity and execution

| Preferred term | Definition and source | Aliases and usage |
| --- | --- | --- |
| Problem | Stable product-level identity containing user intent, intended outcomes, resource scopes, and ordered links to phase-labelled runs. An associated run belongs to at most one Problem; unassociated v1 runs remain valid. [ADR 0012](adr/0012-problem-identity-and-run-ownership.md). | Capitalize for the product-level concept. Lowercase "problem" may describe an ordinary problem. No Problem registry/API or `problem_id` is added to v1. |
| run | Scope owning one graph, its versions, proposals, durable journal, and produced evidence/artifacts. [ADR 0012](adr/0012-problem-identity-and-run-ownership.md), [Protocol](protocol.md#commandquery-plane). | Use `run_id` for the exact protocol identifier. Qualify "agent run" and "evaluator run" in experiments; neither implies a service run. |
| harness session | Harness-owned execution context and native lifecycle, credentials, and optional telemetry. Replaceable independently of Problem and run identity. [ADR 0012](adr/0012-problem-identity-and-run-ownership.md). | "Session" is acceptable when the harness is clear. Never use a session ID as `run_id` or select a run through ambient session state. |
| harness | Runtime that owns model inference, tools, and session execution in the initial PoC. [ADR 0001](adr/0001-harness-neutral-core.md), [Architecture](architecture.md#domaincore). | HarnessX and Claude Code are harness names; ProblemForger is the reliability layer. |
| worker | Model/agent that proposes graph mutations and performs work without owning authoritative graph state. [ADR 0004](adr/0004-external-graph-governor.md). | "Worker model" or "worker agent" may specify the actor. Avoid unqualified "agent" where it could include the governor or verifier. |
| governor | External authority deciding whether a proposed graph mutation commits, using invariants, evidence, verification, and policy. [ADR 0004](adr/0004-external-graph-governor.md). | "Graph governor" and "mutation governance" describe this role and decision process. External means outside worker authority, not necessarily remote. |
| local service | Separate Python process exposing the same versioned application boundary to harness clients. [ADR 0009](adr/0009-separate-local-process-service-boundary.md). | "Core/service" is shorthand only when both are meant. A process boundary alone does not establish worker isolation. |
| harness adapter | Integration translating harness events, tools, and supported actions across the service boundary; it must not contain domain policy. [ADR 0001](adr/0001-harness-neutral-core.md). | "Integration" is broader. The Claude Code plugin packages an MCP bridge, instructions, and hooks; it is not an EventStore provider. [ADR 0011](adr/0011-claude-code-plugin-harness.md). |
| observer | Read-only consumer of graph projections, durable audit projections, and optional telemetry through the service/application API. [UI](ui.md), [Architecture](architecture.md#ui). | UI is outside the correctness path and must not access EventStore directly. |

## Graph and durable state

| Preferred term | Definition and source | Aliases and usage |
| --- | --- | --- |
| problem graph | Explicit run-scoped representation of goals, requirements, work, artifacts, evidence, dependencies, and provenance. [GRAPH.MODEL](problem-graph.md#spec-graph-model). | `ProblemGraph` remains the architectural name, including historical phase titles. Prefer "problem graph" in ordinary prose. It is neither the product-level Problem nor a harness control-flow graph or chain-of-thought archive. |
| root goal | Run-scoped objective represented by a protected `RootGoal` node. [GRAPH.MODEL](problem-graph.md#spec-graph-model), [ADR 0012](adr/0012-problem-identity-and-run-ownership.md). | Preserve exact node kind `RootGoal`; do not conflate it with canonical Problem-level intent or intended outcomes. |
| requirement | Constraint or condition that must remain satisfied; exact node kind `Requirement`. [GRAPH.MODEL](problem-graph.md#spec-graph-model). | Distinguish a graph node from a specification requirement such as `GRAPH.MODEL`. |
| task | Bounded unit of work; exact node kind `Task`. [GRAPH.MODEL](problem-graph.md#spec-graph-model). | Qualify "benchmark task" when describing an evaluation case rather than a graph entity. |
| artifact | Produced object, such as code, patch, file, or test result; exact node kind `Artifact`. [GRAPH.MODEL](problem-graph.md#spec-graph-model). | A graph label alone does not identify checked bytes or satisfy an evidence requirement. |
| protected anchor | Root goal or selected requirement protected from silent worker changes. [ADR 0004](adr/0004-external-graph-governor.md), [GRAPH.MODEL](problem-graph.md#entities-and-provenance). | `protected` is the exact graph field. Other node kinds must have `protected=false`; worker authority does not include protected creation or changes. |
| graph entity | Node or edge with immutable meaning and retained lifecycle/provenance. [GRAPH.MODEL](problem-graph.md#entities-and-provenance). | "Entity" is acceptable in graph context; `entity_kind` is exactly `node` or `edge`. |
| mutation proposal | Client-identified request to change a run graph against an expected graph version. [ADR 0006](adr/0006-authoritative-domain-events-and-stream-concurrency.md), [PROPOSAL-RECOVERY](protocol.md#spec-protocol-proposal-recovery). | "Proposal" or "proposal attempt" is acceptable. Exact `proposal_id` is unique within a run; a receipt is not a commit. |
| proposal receipt | Durable record retaining complete normalized/versioned request input and its identity/hash for recovery. [PROPOSAL-RECOVERY](protocol.md#spec-protocol-proposal-recovery). | Exact record type `proposal_receipt`; pending receipt status `PENDING` is not a governance outcome. |
| governance outcome | One final decision on a proposal attempt: `COMMIT`, `REJECT`, `RETRY`, `ESCALATE`, or `CONFLICT`. It is durable before a completed response. [ADR 0006](adr/0006-authoritative-domain-events-and-stream-concurrency.md). | "Mutation outcome" and "final governance decision" are accepted synonyms. Qualify "outcome" where it could mean a benchmark result or Problem-level intended outcome. |
| proposal status | Pending, abandoned, or final governance status exposed for a proposal. [Protocol](protocol.md#version-1-request-and-response-schema). | `PENDING` and `ABANDONED` are operational statuses, not additional governance outcomes. Preserve protocol table terminology. |
| entity lifecycle | Committed entity state: `active`, then optionally `superseded` or `invalidated`; inactive states are terminal in graph-v1. [ADR 0007](adr/0007-separate-lifecycle-verification-and-evidence-axes.md), [GRAPH.MODEL](problem-graph.md#operations-and-graph-events). | "Verified" is not an entity lifecycle state. An `invalidates` or `supersedes` edge alone does not change lifecycle. |
| durable run journal | Append-only run-scoped sequence containing governance audit records and graph-changing domain events. [ADR 0006](adr/0006-authoritative-domain-events-and-stream-concurrency.md). | "Journal" is acceptable in run context. "Event log/stream" remains valid in ADR history; qualify current prose to distinguish journal records from telemetry. |
| governance audit record | Durable proposal receipt, non-terminal audit record, or final governance/operational record that does not itself change graph state. [MODULES.EVENTSTORE-PORT](modules.md#journal-records-and-version-domains). | "Audit record" is acceptable. Exact types include `proposal_receipt`, `non_terminal_audit`, `mutation_decision`, and `proposal_abandoned`. |
| graph-changing domain event | Committed graph change used to reconstruct graph state. [ADR 0006](adr/0006-authoritative-domain-events-and-stream-concurrency.md). | "Graph event" is acceptable when clearly distinguished from telemetry. Journal type `graph_changed` wraps a nested event type such as `node_created`. |
| mutation batch | Atomic commit decision and one or more graph events, advancing graph version exactly once. [ADR 0006](adr/0006-authoritative-domain-events-and-stream-concurrency.md), [EventStore](modules.md#spec-modules-eventstore-port). | "Committed batch" is acceptable. An individual event is not an independently addressable intermediate graph version. |
| journal position | Per-run ordering position assigned to every durable journal record. [MODULES.EVENTSTORE-PORT](modules.md#journal-records-and-version-domains). | Exact `journal_position`; not graph version or schema version. |
| graph version | Monotonic committed graph-state version, advancing once per complete committed mutation batch. [ADR 0006](adr/0006-authoritative-domain-events-and-stream-concurrency.md). | Exact `graph_version`; `expected_graph_version` is the caller's precondition. Audit-only writes do not advance it. |
| graph projection / replay | Projection is derived graph state; replay reconstructs it from complete committed graph batches in journal order. [ADR 0002](adr/0002-event-sourced-authoritative-state.md), [GRAPH.MODEL](problem-graph.md#batch-validation-and-replay). | Replay excludes optional telemetry and does not rerun governor policy or evidence producers. Preserve exact `GraphProjection` where referring to the implementation. |
| transport retry | Resubmission of the same proposal identity and normalized request after an uncertain response; resumes or replays that attempt. [PROPOSAL-RECOVERY](protocol.md#proposal-recovery-responses). | Distinct from governance `RETRY`, which ends the attempt. A semantic retry needs a new `proposal_id` with causal linkage. |

## Evidence, integration, and evaluation

| Preferred term | Definition and source | Aliases and usage |
| --- | --- | --- |
| evidence | Scoped support for or contradiction of a claim/entity/mutation, retaining origin, method, subject, result, provenance, and optional uncertainty. [ADR 0007](adr/0007-separate-lifecycle-verification-and-evidence-axes.md). | Exact node kind `Evidence` is separate from an evidence record/reference. A worker assertion or digest alone is not trusted support. |
| evidence origin | Who or what produced the evidence. [Verification](verification.md#origin). | Prefer "origin" over ambiguous "source" for this metadata axis. Origin is separate from verification method. |
| verification method | How evidence was obtained, such as assertion, deterministic check, observed outcome, learned judge, or human review. [Verification](verification.md#method). | "Deterministic", "observed", and "learned" do not form a global evidence-strength rank. |
| trusted provenance | Service-assigned producer identity/origin through an approved evidence-producing integration. [EVIDENCE-TRUST](verification.md#spec-verification-evidence-trust). | Worker-supplied provenance is a claim. Trusted origin does not prove checker correctness. |
| evidence binding | Immutable association between evidence, exact checked subject/content, checker version/configuration, and necessary external inputs. [EVIDENCE-BINDING](verification.md#spec-verification-evidence-binding). | `subject_digest`, `checker_version`, and `(run_id, entity_id, graph_version)` retain exact specification meanings. A hash binds content, not trust. |
| verification status | Projection over evidence and policy, separate from mutation outcome and entity lifecycle. [ADR 0007](adr/0007-separate-lifecycle-verification-and-evidence-axes.md). | "Verification state" is an accepted prose synonym. Labels such as "locally supported" or "disputed" are possible derived labels, not fixed lifecycle values. |
| verifier / evaluator | A verifier contributes scoped evidence; the benchmark evaluator applies the frozen task success rule. [Verification](verification.md#learned-verifier), [Evaluation](evaluation.md#spec-evaluation-measured-evaluation). | Do not use interchangeably where actor authority matters. A verifier score is not ground truth; candidate code is outside trusted evaluator authority. |
| telemetry observation | Optional, non-authoritative harness/model/tool/runtime observation. [ADR 0006](adr/0006-authoritative-domain-events-and-stream-concurrency.md), [TelemetrySink](modules.md#spec-modules-telemetry-port). | "Observation event" is acceptable in telemetry context. `TelemetrySink` receives observations; they do not advance journal position or graph version. |
| native trajectory archive | Harness-owned raw execution artifact retained externally for reproducibility. [Architecture](architecture.md#modulesadapters). | Optional normalized telemetry is not a complete native trajectory. Neither belongs in the authoritative journal. |
| port / provider / module | A port is a replaceable capability interface; a provider is its concrete implementation, packaged as a module with provider-specific configuration. [ADR 0003](adr/0003-ports-adapters-config-modules.md). | Preserve exact `EventStore` and `TelemetrySink`. Avoid using "adapter" alone for a provider when harness integration could be meant. |
| composition root | Explicit configuration/registry wiring that constructs providers and passes ports into application code. [Architecture](architecture.md#composition-root-and-configuration). | Provider selection is defined in [Modules](modules.md#provider-registry). No dynamic class imports or generic service locator are implied. |
| durable / ephemeral provider | Durable providers support journal survival/recovery across restart; memory is ephemeral and test-only. [ADR 0003](adr/0003-ports-adapters-config-modules.md). | Exact capability values `durable` and `ephemeral`; `MemoryEventStore` cannot serve the normal durable profile. SQLite is the first durable provider. |
| JSON Lines | UTF-8 JSON messages delimited by newlines on the selected Unix-domain stream socket transport. [ADR 0010](adr/0010-local-service-transport.md). | "JSONL" is the accepted abbreviation. MCP is the Claude Code outer adapter, not a replacement transport. |
| PoC / P0 through P11 | PoC means proof of concept. P0 through P11 name the repository's phases. [PLAN.md](../PLAN.md#phase-order). | Phase names indicate planned scope, not evidence of completion. P6 is the initial practical pilot; P11 is a separate later ablation/portability study. |
| P6-AC / A / B / C | P6-AC compares pinned HarnessX baseline A with complete graph/governance package C. B is graph without governance, an optional separately frozen diagnostic. [ADR 0005](adr/0005-ablation-first-evaluation.md). | "A/C pilot" is acceptable. A/C does not isolate graph or governance effects. B results and later harness studies must not be pooled with P6. |
| slot / agent attempt / evaluator invocation | A slot is one planned task/configuration entry; an eligible first failure may require one clean agent retry. Each produced patch has at most one evaluator invocation; evidenced invalid patches are not dispatched. [Evaluation](evaluation.md#execution-controls). | Avoid calling every slot or attempt a service run. Twelve planned A/C slots do not imply exactly twelve actual attempts or evaluations. |
| manifest | Frozen experiment inputs, identities, settings, tasks, metrics, and limits retained with their hash. [EVALUATION.PRE-P6](evaluation.md#spec-evaluation-pre-p6). | An execution image pins environment bytes, not opaque hosted-model weights or exact future inference. |
| observed failure / missing outcome | An observed failure is an evidenced terminal zero; incomplete mandatory evidence leaves the outcome undefined. [Evaluation](evaluation.md#spec-evaluation-measured-evaluation). | `EVIDENCE_INCOMPLETE` is slot-level missing evidence; `INCOMPLETE_EVIDENCE` stops new work for shared evidence failure. Do not normalize these distinct identifiers. |
| calibration / abstention | Calibration estimates verdict correctness using task-level held-out data; abstention declines a verdict under the declared policy. [Verification](verification.md#calibration), [PLAN.md](../PLAN.md#phase-order). | Raw model confidence is not calibrated probability. Preserve `Brier`, `ECE` (expected calibration error), and `OOD` (out of distribution) in technical prose. |
| model suitability / routing | Suitability estimates success conditional on node, graph state, model, and budget; routing uses such estimates under uncertainty. [Model routing](model-routing.md#target). | Not a global node-difficulty score or fixed model rank. Inference remains harness-owned; active routing is later work. |

## Unresolved wording for review

These passages remain unchanged because editing them could choose technical
semantics. They do not create exceptions to higher-authority contracts.

- [Graph versioning](problem-graph.md#versioning-and-concurrency) says owners
  define "lease" algorithms; [ADR 0006](adr/0006-authoritative-domain-events-and-stream-concurrency.md)
  and [deferred claims](protocol.md#spec-protocol-parallel-claims) defer leases.
  Confirm whether this is a stale summary or a reference to future work.
- [Protocol command/query operations](protocol.md#commandquery-plane) say run
  creation returns its ID; the concrete v1 schema requires a supplied `run_id`.
  [Modules](modules.md#service-clock--id-source) also mentions an ID source for
  run IDs. Confirm which actor allocates IDs in each integration before
  changing that guidance. Explicit run identity remains required.
- [Methodology](methodology.md#measurement) says a task is resolved only when
  its required test vector completes; [Evaluation](evaluation.md#spec-evaluation-measured-evaluation)
  also defines evidenced `NO_PATCH` and `CANDIDATE_PATCH_INVALID` terminal zeros.
  Confirm whether "resolved" means successful or merely a defined binary outcome.
  Keep success, observed failure, and missing evidence distinct.
